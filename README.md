# Устройство для считывания штрихкодов на конвейере

## 1. Обзор решения

Комплекс считывает штрихкоды со всех шести граней движущейся коробки с помощью шести камер (2 линейные + 4 матричные, по одной на грань), детектирует штрихкоды нейросетью, декодирует промышленным SDK и передаёт результат в PLC конвейера. Обработка полностью локальная.

## 2. Камеры

| Позиция | Тип | Модель | Разрешение / матрица | Кол-во |
|---|---|---|---|---|
| Верх / низ | Line Scan, цвет. | Teledyne DALSA Linea, цветная версия (GigE Color, 8K) | 8192 px, Global Shutter, 57.3 мм | 2 |
| Лево / право | Area Scan, цвет. | Basler ace 2 a2A2500-19gcPRO | 25 Мп (5472×4608), Sony IMX571, 14.96×12.58 мм | 2 |
| Перед / зад | Area Scan, цвет. | Basler ace 2 a2A2500-19gcPRO | 25 Мп (5472×4608), Sony IMX571, 14.96×12.58 мм | 2 |

Цветной сенсор выбран, поскольку распознавание опирается на цветовой контраст штрихкода к пёстрому фону картона. Лево/право и перед/зад используют одну и ту же модель камеры (25 Мп) - различаются только объективом и рабочей дистанцией; это даёт всем четырём позициям одинаковый пиксельный бюджет и, соответственно, одинаковый запас по покрытию грани и разрешению, а заодно упрощает закупку и склад запчастей.

### 2.1 Объективы и подсветка

Верх/низ: Schneider Kreuznach MegascanPlus 1.8/50, M58/M72 (2 шт). Лево/право: объектив формата 1.1″, 16 мм (напр. Fujinon HF16SA-1), C-Mount (2 шт). Перед/зад: объектив формата 1.1″, 35 мм (напр. Fujinon HF35SA-1), C-Mount (2 шт) - формат объектива подобран под увеличенный сенсор 25 Мп. Подсветка: линейные LED Advanced Illumination HT-50 (2 шт, стробоскоп, синхронизация с энкодером); кольцевые LED Smart Vision Lights LFR2-100-WHT - по одной на каждую матричную камеру, итого 4 шт, под общим контроллером LFR2-E.

## 3. Геометрия и параметры съёмки

Требование к разрешению задаётся минимальным элементом штрихкода. Консервативная оценка для типового штрихкода на транспортной таре (GS1-128/Code128) - ширина модуля 0.33 мм (обычный диапазон для таких кодов 0.33–0.5 мм); при правиле не менее 3 пикселей на модуль это даёт требование ≤0.11 мм/px. FOV рассчитан по формуле FOV = (размер матрицы × рабочая дистанция) / фокусное расстояние. Лево/право и перед/зад намеренно рассчитаны на одинаковый запас (≈12% по покрытию грани, ≈11% по разрешению) - за счёт одинакового сенсора, см. п. 2.

| Позиция | Объектив | Дистанция | FOV (мм) | Разрешение | Кадров |
|---|---|---|---|---|---|
| Верх/низ | 50 мм | 600 мм | 688 × 600 | 0.079 мм/px | 1 (непрерывно) |
| Лево/право | 16 мм | 570 мм | 535 × 450 | 0.098 мм/px | 2 на камеру |
| Перед/зад | 35 мм | 1250 мм | 534 × 450 | 0.098 мм/px | 1 |

Боковая грань 600×400 мм: одна камера на сторону, FOV 535×450 мм покрывает высоту грани (400 мм) с запасом ≈12%; по длине грани (600 мм) камера снимает 2 кадра с перекрытием 20% (шаг ≈428 мм), используя движение коробки через тоннель. Грань перед/зад - 400×400 мм, целиком помещается в один кадр (534×450 мм) при увеличенной рабочей дистанции - дополнительные камеры не нужны.

### 3.1 Тоннель и синхронизация

Длина тоннеля пересчитана под текущую геометрию: зона захвата боковых камер - FOV (535 мм) плюс шаг между двумя кадрами (428 мм) ≈ 963 мм, плюс ≈240 мм на позиционирование фотодатчика входа и гарантированный выход коробки из зоны съёмки ⇒ длина тоннеля ≈1200 мм. Нижняя секция ленты в зоне тоннеля прозрачна (закалённое стекло либо поликарбонат) для нижней камеры. Выходной портал тоннеля - не далее 3 м от узла сортировки, что при скорости 1 м/с даёт ≈3 с на вычисления и передачу решения в PLC.

Инкрементальный энкодер на валу конвейера синхронизирует триггеры камер с положением коробки. Фотоэлектрический датчик SICK WTB4-3 на входе тоннеля фиксирует переднюю кромку коробки и создаёт виртуальный объект Box с привязкой к тику энкодера.

### 3.2 Количество кадров на коробку

2 (линейные, непрерывно) + 2 (лево) + 2 (право) + 1 (перед) + 1 (зад) = 8 кадров на коробку через 6 физических камер.

## 4. Вычислитель

Суммарный объём сырых данных на коробку - около 266 Мп (2×57.3 Мп линейные + 4×25.2 Мп боковые + 2×25.2 Мп торцевые); при интервале между коробками 2 с это укладывается в возможности одной сетевой карты и локального SSD с большим запасом - специализированное сетевое или дисковое оборудование не требуется.

Бюджет по времени задаётся ТЗ (устройство не далее 3 м от узла сортировки → ≈3 с на вычисления после выхода из тоннеля) и интервалом между коробками (2 с - столько в среднем может уходить на обработку одной коробки, чтобы не копилась очередь). Поскольку все 8 кадров перед детекцией приводятся к одному размеру 640×640, время инференса на кадр одинаково независимо от камеры; для восьми кадров типовой CPU-сервер (например, Intel Core i7, OpenVINO INT8) обрабатывает всю партию за ориентировочно 110–140 мс - локальная обработка комфортно справляется без GPU и без специальных мощностей. GPU можно держать в резерве как задел на будущее (рост скорости конвейера, больше камер или классов детекции), но для текущей задачи он не обязателен.

Облачная обработка не рассматривается: передача данных за пределы предприятия и обратно занимает секунды-десятки секунд в зависимости от канала связи - на порядок больше локального бюджета, поэтому весь инференс и декодирование выполняются на edge-сервере рядом с конвейером. В облако (или на локальный MinIO-архив) уходят только сырые кадры асинхронно - для аудита и дообучения модели, вне цепочки принятия решения.

## 5. Поток данных

Camera Ingestor → Kafka (сырые кадры) → Inference Worker (RT-DETR-L) → Kafka (детекции) → Decoder Worker (Dynamsoft SDK) → Kafka (декодированные коды) → Aggregator (привязка к коробке по тикам энкодера, дедупликация) → Kafka (решения) → PLC Gateway (OPC UA) → контроллер конвейера. Параллельно: MinIO Consumer сохраняет сырые кадры на 24 ч для аудита и дообучения; Prometheus + Grafana собирают метрики и алерты.

Kafka обеспечивает надёжную доставку и партиционирование по камерам с возможностью повторной обработки при сбое сервиса. MinIO - локальное S3-совместимое хранилище, данные не покидают периметр предприятия. Prometheus/Grafana - локальный мониторинг без выхода в облако. OPC UA - стандарт Industry 4.0 с шифрованием и поддержкой сложных структур данных для связи с PLC.

## 6. Предобработка и нейросеть

Демозаика (Bayer → RGB) выполняется перед подачей кадра в сеть. Undistortion по карте искажений объектива критична на высоком разрешении для сохранения прямых линий штрихкода и точности bounding box.

Модель - RT-DETR-L: детекция без NMS (не теряет близко расположенные штрихкоды на одной грани), self-attention для мелких объектов, GIoU loss и transformer-decoder для точной локализации рамок под последующий кроп. Backbone HGNetV2. После обучения - конвертация в TensorRT/OpenVINO, FP16/INT8.

Пайплайн детекции (detect on low-res, decode on high-res): кадр ресайзится до 640×640 для инференса (один проход на кадр), координаты масштабируются обратно на оригинал, из полноразмерного кадра вырезается кроп для декодера.

## 7. Декодирование и агрегация

Decoder Worker вырезает область интереса с запасом 10–15% по краям, передаёт в Dynamsoft Barcode Reader: включены только нужные форматы, приоритет скорости, коррекция перспективы и восстановление повреждённых кодов. Нераспознанные детекции отбрасываются, что снижает ложные срабатывания от текстур картона.

Aggregator привязывает штрихкоды к коробке по тикам энкодера: фотодатчик на входе тоннеля создаёт виртуальный объект коробки, каждый тик энкодера обновляет позиции активных коробок, штрихкод привязывается по совпадению тика съёмки с позицией коробки. Дедупликация убирает повторы от перекрытия соседних кадров. Состояние хранится в памяти процесса.

## 8. Масштабирование

**Новый тип штрихкода:** RT-DETR-L детектирует все штрихкоды одним классом barcode - переобучение не требуется; Dynamsoft поддерживает большинство форматов штрихкодов - включить в конфиге декодера. Время внедрения: 8 работо часов

**Новый класс объектов (напр. логотип):** дообучение RT-DETR-L на втором классе, +2000 размеченных изображений, 4–6 ч на RTX 4070. Время внедрения: 56 рабочих часов

**Изменение скорости конвейера:** при росте скорости доступное окно на вычисления сокращается - запас у CPU-варианта остаётся. Частота энкодера растёт пропорционально скорости, программных изменений, кроме пересчёта временных констант триггеров, не требуется.

**Другой форм-фактор коробки:** система параметризована размерами коробки в конфиге. При изменении габаритов пересчитываются число кадров на грань и рабочие дистанции камер. Перенастройка в пределах ± 25% от текущих габаритов - сменой профиля в конфиге, за этим порогом - физическая замена объектива.

## 9. Датасет и обучение

Расчёт минимального объёма: N = (I_base × V_factor) / (A_avg × W_factor) = (15000 × 2.0) / (2 × 5) = 3000 изображений; с запасом 20–30% на валидацию/тест и редкие edge-кейсы - 4000 изображений. W_factor - коэффициент аугментации обучающего датасета через нарезку каждого исходного изображения на 5 перекрывающихся патчей; в рабочем пайплайне (п. 6) патчи не используются.

**Разметка:** связка Grounding DINO (zero-shot детекция по промпту, начальные bounding box) + SAM3 (уточнение границ/масок) сокращает ручную разметку на 70–80% - оператор только корректирует. После разметки выполняется дедупликация визуально почти идентичных последовательных кадров.

**Аугментация:**
- геометрическая: повороты ±15°, случайный перспективный сдвиг, отражение по горизонтали;
- фотометрическая: изменение яркости/контраста, имитация бликов от подсветки, цветовой шум сенсора;
- имитация дефектов: motion blur, гауссов шум, частичная окклюзия/заломы наклейки, снижение контраста при загрязнении;
- нарезка на перекрывающиеся патчи (sliding window) для увеличения числа обучающих примеров с сохранением масштаба объекта.

## 10. Ключевые метрики

| Метрика | Что измеряет | Цель |
|---|---|---|
| Detection Rate | Доля реально присутствующих штрихкодов, найденных сетью (recall по инстансам, не по кадрам) | ≥ 98% |
| Decode Rate | Доля найденных штрихкодов, успешно прочитанных SDK | ≥ 99% |
| Sort Accuracy | Верность выбора линии отвода - считается только по коробкам, для которых решение было принято (штрихкоды с контрольной суммой практически исключают неверное, но «успешное» считывание) | ≥ 99% |

При Detection Rate 98% и Decode Rate 99% доля коробок с полностью прочитанными штрихкодами - около 97%; оставшиеся ~3% помечаются NO_READ и уходят на ручную сортировку (не считаются ошибкой Sort Accuracy, так как решение по ним не принималось автоматически).

Проверка на практике: анализ корзины ручной сортировки (коробки NO_READ разбираются оператором и пополняют датасет дообучения), выборочный ручной аудит успешно отсортированных коробок (5–10 за смену), внутренняя согласованность (конфликт детекции/декодирования или расхождение показаний соседних камер переводит коробку в статус «подозрительная» для ручной проверки). Все метрики собираются Prometheus и визуализируются в Grafana.
